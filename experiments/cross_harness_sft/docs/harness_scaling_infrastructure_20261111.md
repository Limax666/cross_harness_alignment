# Harness Scaling infrastructure: CPU prototype and admission boundary

The new `rl_harness_scaling.py` exposes the paper's Table 6 five-factor array and a deterministic, seeded K=2 nearest-neighbor assignment ledger. Its task IDs and versions must refer to already audited, split-safe tasks. This ledger does not create task cells, enforce clean/attack semantic equivalence, freeze component content, or establish train/test exclusion. Do not substitute it for the legacy ledger without those checks.

`rl_harness_segments.py` provides a framework-neutral prototype for capturing the exact token prefix and sampled tokens/log probabilities of each generation call, computing group-normalized advantages over original rollouts (sample standard deviation), and expanding the records for token-level loss. Generation calls are independently represented: prefix tokens carry no loss, generated tokens occur once. Callers must record the actual `prompt_ids` passed to inference, not reconstruct a prompt from messages. `token_mean` is an arithmetic helper, not an integrated distributed VeRL reduction; microbatch/distributed normalization must use the global valid-token count, not an average of per-segment or per-microbatch means.

`compact_history` is a policy primitive operating on caller-defined complete turns. C1 keeps five recent turns and puts the caller's summary in context; C2 keeps three and returns an external summary. The caller must supply an appropriate summarizer, preserve earlier summaries across repeated compactions, store C2 summaries in a resettable isolated workspace with auditable read access, and protect system instructions, tool schemas, authorization and message boundaries. The helper alone does none of these. Summaries and tool content remain untrusted; the prototype is not a production compactor.

The old whitebox path continues to fail closed for C1/C2. No new module is connected to the live loop, VeRL batch expansion, old/reference log-prob computation, actor loss, or CHS-PO. Before enabling C1/C2, implement and validate those connections end to end, including context-length and tokenizer boundaries, multi-turn grouping, policy version consistency, rollout scoring and optimizer reduction across distributed microbatches. Verify real environment resets, side effects, external summary access, and full GPU update/weight synchronization in a separately authorized resource preflight. Do not claim the five-factor experiment or RSI is runnable based on these CPU primitives.

## Online CPU adapter (follow-up)

`rl_harness_online.py` adds a per-rollout context session: caller-supplied complete serialized turns, protected context, repeated C1/C2 summaries, hash-only compaction audit events, and an async sampling wrapper that records exactly the token tuple sent to the generator and rejects a mismatched policy version. C2 summary storage is session-local memory exposed through `read_external_summary`, not a real workspace file or registered tool. A summarizer and renderer must be supplied by the caller. The summarizer receives the previous summary and removed turns; it is responsible for preserving their content without turning untrusted text into instructions. The protected tuple is only an adapter contract, not proof that a tokenizer/chat template or tool schema is valid.

`policy_loss_parts` divides each local numerator by the same explicitly supplied global token count, allowing microbatch contributions to be summed without weighting segments equally. The caller must verify the count across the complete batch and account for distributed gradient averaging. CPU tests use a deterministic generator and finite-difference arithmetic; no real model, actual VeRL `DataProto`/actor, PyTorch distributed optimizer, live summarizer, file-backed C2 tool, or GPU training has been verified. The legacy entry continues to reject C1/C2.

## Segment DataProto bridge

`rl_harness_segment_dataproto.py` packs each generation call into one independently padded prompt/response row. It carries precomputed rollout-level advantages and original rollout/group identifiers, rejects inconsistent parent metadata and length overflow, and exposes `make_dataproto` to create VeRL `DataProto` tensors. The result deliberately omits `old_log_probs` and reference log probabilities: recompute them with the actor/reference using each row's full prefix. Do not apply VeRL's GRPO normalization again to expanded rows. The bridge is not connected to the training driver and does not assert that downstream code respects its metadata.

The inspected VeRL `agg_loss` implements global `token-mean` as local masked token sum times data-parallel size divided by global valid-token count. This is the right form only when the count spans the entire optimizer minibatch, all microbatches are accumulated consistently, and the backend averages gradients over those ranks. An integration test exercises actual `DataProto`, VeRL `agg_loss`, and PyTorch autograd with uneven simulated rank token counts; it requires the project's working PyTorch/VeRL environment and has not been established as passing when PyTorch import is blocked by host I/O. It does not exercise real multi-process distributed training.

## Actor/reference scoring bridge

`rl_harness_segment_actor_bridge.py` can call the existing VeRL trainer's old-policy and reference scoring methods with the same expanded `DataProto`, check their response-aligned shapes and finite values, and attach the results without recalculating advantages. It rejects sequence-level loss reduction and an expanded batch larger than the declared optimizer minibatch capacity. That capacity check is necessary but not sufficient to establish distributed gradient correctness or worker batching behavior. The helper neither calls `_update_actor` nor replaces whitebox rollout evidence, safety admission, CHS-PO constraints or checkpoint accounting. It is not connected to the production trainer; the old C1/C2 guard remains in place.

## GRPO preparation and original-rollout admission

`rl_harness_segment_pipeline.prepare_segmented_step` connects rollout-level GRPO normalization, segment DataProto construction, VeRL old/reference scoring methods and `admit_segmented_rollouts`. The last reconstructs one generated-token record per original rollout and invokes the existing `require_online_batch` safety gate, including G=4, assignment, policy snapshot and verifier checks. It rejects mismatched recorded segments, rewards, groups and evidence. The preparation path is independent, requires explicit use, supports GRPO only and returns the admitted batch without invoking an optimizer. It does not install itself in `RayPPOTrainer.fit`; CHS-PO, KL-in-reward, rollout correction, distributed minibatch behavior, real context compaction, and actor optimizer/checkpoint integration remain unimplemented or unverified. Callers must not submit the result for training until these gates and live end-to-end validation have passed.
