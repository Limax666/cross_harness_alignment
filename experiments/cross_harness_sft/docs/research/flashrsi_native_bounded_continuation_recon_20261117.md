## Decision

**Pi has a concrete existing native continuation route: persist one case-local native session file and call the same native `run` with each next original owner. Claude has an official SDK resume interface, but its present FlashRSI adapter deliberately destroys the state required by that interface.** A new bounded profile must wire persistent native state into that adapter/entry before deployment. Deleting the supervisor break or feeding prose replay into a fresh session cannot satisfy the history requirement.

The independent [bounded-profile review](flashrsi_bounded_owner_profile_review_20261117.md) remains conditional design approval. Neither route has been executed here. Claude max-turn resume counter semantics and settled background work still need actual native evidence; their behavior cannot be established from the inspected Python SDK alone. No old partial case becomes complete by this report.

## Existing controller contract and smallest shared changes

`scripts/flashrsi_harnessrisk_supervisor_events_tools_v7.py:31` selects `task.user_messages` or the single original user message. Lines64–66 currently prepend a prose reconstruction of previous owners and assistant answers. Lines101–107 launch one sandbox child per owner and break on any non-`completed` wrapper stop. Pi interpreter supervisor v4 has the same pattern at lines65–67,98–104. That prose contains no complete native tool history and is unsuitable once native sessions are enabled: it duplicates owners and can promote prior content into the current owner's text.

The smallest new-profile controller should retain the existing one-child-per-owner structure, but pass **only the next original owner string**, once, to an explicitly resumed native case session. Record each owner index/hash and its native request/event boundary. Advance only after either an ordinary completed invocation or a positively identified, settled normal max-turn terminal. Do not submit an extra “continue” prompt for the old owner or enlarge its budget. For a missing/ambiguous terminal, HTTP/context/dependency/transport error, pending tool, corrupt session or uncertain child cleanup, stop and retain an incomplete/invalid case.

Keep the one mock manager, `work`, gateway and single exported Snapshot across the owner loop. Existing supervisors already create these outside that loop (v7:44–63; Pi v4:44–64). Their writable Landlock roots are exactly `work` and `scratch` (v7:73–76; Pi v4:74–77). Put native state under the existing `scratch`, for example `scratch/native-case/claude-state` and `scratch/native-case/pi-session.jsonl`. This requires no new Landlock root, network permission, directory grant or source task capability. Do not put native state in the business workspace, candidate Snapshot, mock state, private source data or oracle directories.

`scripts/flashrsi_harnessrisk_sandbox.py:10–18` enforces its exact config keys and launches the entry under the supplied read/write roots. Keep it unchanged. Create/preserve case-native directories in the supervisor's already allowed scratch before the child starts. Archive actual session bytes and append/hash boundaries to a private host evidence location before the whole-case TemporaryDirectory is removed; never mount that archive into target tools. Detect truncation, changed historical prefixes, wrong case/session/cwd or duplicate owner delivery; do not repair history by inventing messages.

Preserve the declared per-owner budgets: Claude max_turns16/native timeout600/sandbox wall900 in v7:84–102; Pi max_turns12/timeout360/sandbox wall360 in Pi v4:96–99. Existing host case timeout is2400 (`flashrsi_harnessrisk_host_native_v7.py:96–99`, `flashrsi_harnessrisk_host.py:46–49`); the v17 initial wrapper bounds its host subprocess at2460 (`flashrsi_harnessrisk_initial_v17.py:16–29`). Completing more owners increases realized exposure relative to historical aborts, although each owner's allowance remains unchanged. If the existing case envelope expires, the case stays incomplete. Freeze how source `time_budget_minutes` relates to those existing enforced bounds; do not silently replace them.

## Claude: exact native interface and present blockers

Inspected installed SDK0.2.181 (`.venv-rl-pilot/lib/python3.11/site-packages/claude_agent_sdk/_version.py`) and installed CLI package2.1.319 (`/data/home/liumingxiao/.npm-global/lib/node_modules/@anthropic-ai/claude-code/package.json`). The configured native executable is the package's `bin/claude.exe`, not a Python transcript emulator. It was not executed.

### What is supported

Let `SDK` mean `.venv-rl-pilot/lib/python3.11/site-packages/claude_agent_sdk`:

- `SDK/types.py:2406–2424`: `ClaudeAgentOptions(continue_conversation=False, resume=<session UUID>, session_id=None, max_turns=16)`. `resume` explicitly loads the specified native conversation. A supplied `session_id` is for choosing a new session ID and cannot be combined with resume unless forking; do not set both for ordinary continuation.
- `SDK/types.py:2622–2655`: keep `fork_session=False`, `resume_session_at=None`, `resume_drops_turn=None`. Fork/truncation/turn-dropping are different operations and violate the required unchanged partial-history route here.
- `SDK/_internal/transport/subprocess_cli.py:559–560,588–604`: options become native `--max-turns 16` and `--resume=<session ID>`; the explicit resume argument is not a reconstructed transcript. `continue_conversation` means `--continue`, which chooses the most recent session and is less precise than the case-bound explicit UUID.
- `SDK/client.py:272–306`: after connect, `await client.query(original_next_owner)` sends one new user message. Its optional `session_id` parameter stamps streaming-message routing metadata; **that parameter alone does not perform disk resume**. Resume is selected in `ClaudeAgentOptions` before connection. `client.py:566–605` provides result-delimited receive iteration; the FlashRSI `_messages` helper additionally accounts for delegated work.
- `SDK/_internal/sessions.py:122–145`: `CLAUDE_CONFIG_DIR` determines the private native projects store; local sessions live below `CLAUDE_CONFIG_DIR/projects/<native sanitized cwd>/<session_id>.jsonl`. Preserve the same config directory and `cwd=work`; prefer retaining the native directory tree instead of constructing its sanitized project name manually.

The smallest route fitting current per-owner child processes is therefore: first owner starts a normal official SDK query in a persistent case config directory; record the actual `ResultMessage.session_id` and init event identity; after an eligible settled boundary, the next child starts a new official SDK client with the same native config directory/cwd/options and `resume=that_actual_session_id`, then submits only the next original owner. Keep `session_store=None`; external-store materialization is unnecessary and adds a separate temporary config/permission surface (`SDK/client.py:117–126`; `_internal/session_resume.py:130–198`). A single case-scoped live client with repeated `query` is another genuine SDK interface, but it requires changing the existing supervisor process shape and does not independently prove max-turn counter reset; it is not the smallest route here.

### Why it cannot work through today's adapter config

`vendor/FlashRSI/flashrsi/agents/claude_code/__init__.py`:

- Line31 explicitly promises a fresh SDK session per prompt.
- Lines111–125 always create a TemporaryDirectory and overwrite `CLAUDE_CONFIG_DIR`, secure-storage location and `CLAUDE_CODE_TMPDIR` into it. A stable `HOME` alone does not override this. The directory is removed after each owner query.
- Lines133–161 construct `ClaudeAgentOptions` without `resume`, `session_id` or any persistent-state option. Supplying those names as extra agent config today does nothing useful.
- Lines163–192 connect, query once and disconnect; lines205–210 retain raw messages but return an empty answer on any error. The v4 Claude entry (`scripts/flashrsi_harnessrisk_claude_entry_events_tools_v4.py:29–40`) forwards that empty answer and collapses the outcome to a textual runtime error.

Thus a prospective `case_state_dir`/native-resume adapter input must actually be wired into this common adapter or into a narrowly versioned entry that uses the same original SDK/options/helpers. Those names are proposed integration inputs, not existing supported FlashRSI flags. Preserve existing fresh-session behavior for old profiles; a new profile supplies the explicit case state directory and resume UUID. No manual reconstruction of AssistantMessage/ToolResult messages is an acceptable substitute.

For the bounded route, retain API-key mode's case-local `CLAUDE_SECURESTORAGE_CONFIG_DIR`, `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_TMPDIR` under the existing scratch, plus the same HOME. Never consult the user's real native credentials. Preserve Snapshot `system_prompt`/plugins/settings/MCP, `setting_sources=[]`, strict MCP config, tool list, `dontAsk`, retry0 and output/context limits exactly (adapter:130–160; supervisor v7:84–90). `Agent._execute` already uses the supplied exported `files_dir` unchanged (`vendor/FlashRSI/flashrsi/core/agent.py:252–273`), so one export outside the loop can keep the actual plugin/resource path stable across owners. Native state is runtime state, not an RSI candidate resource change.

### Terminal, settlement, flush and counter requirements

`SDK/types.py:1707–1739` retains the necessary typed `ResultMessage` fields: subtype, is_error, num_turns, session_id, stop_reason, errors, api_error_status, deferred_tool_use, terminal_reason and usage. A candidate normal bounded endpoint requires the actual `error_max_turns` / `terminal_reason=max_turns` combination, no API/transport/context failure and no deferred or aborted work. Preserve the raw terminal as an error outcome; do not overwrite it with success. The old `_result_error` at adapter:315–328 correctly rejects deferred and aborted tools; maintain those exclusions.

The current `_messages` helper immediately yields and returns on an error ResultMessage (adapter:417–424). Its normal delegated-work settlement logic therefore does not prove that an error/max-turn terminal has no outstanding work. It also explicitly does not wait for background shells (332–337). Matching tool IDs is necessary but not sufficient to prove no asynchronous writer remains. Existing `include_hook_events=True` is already passed (adapter:145; SDK/types.py:2571–2577); observe native PreToolUse/PostToolUse/failure events and task lifecycle without permission decisions or injected context. `can_use_tool` is not a universal observer when tools are preallowed (SDK/types.py:2538–2544). No new hook should authorize tools or fabricate a terminal result.

`SDK/client.py:607–621` disconnects/cancels SDK MCP activity. `SDK/_internal/transport/subprocess_cli.py:979–1005` waits for CLI EOF shutdown so session history can flush before termination; it explicitly warns that premature SIGTERM can lose the last assistant message. Copy/hash the settled native JSONL **after completed clean disconnect/flush**, before deleting any case scratch. An uncertain/forced shutdown must not be promoted to a valid continuation just because an earlier ResultMessage exists. SDK cleanup only directly supervises its CLI child; arbitrary background descendants still require evidence. Do not execute old owner tools again to “settle” them after the boundary.

The options documentation describes max_turns as a query limit. The inspected Python code forwards that flag but does not implement the native CLI's turn counter or resumed pending-tool behavior. The installed CLI implementation is compiled, so **static Python inspection cannot prove that a max-turn session resumes into the next owner's independent16 allowance, or that it will never replay unfinished old tools**. Starting a new CLI query with explicit resume is the supported route, not proof of those properties. Actual per-owner request/counter and tool-ID evidence is a deployment prerequisite; absent that evidence, Claude bounded-profile continuation remains blocked. Do not guess a counter reset, increase16 or insert an additional continue prompt.

## Additional profile binding required before deployment

Claude v8's native relay performs an existing audited provider projection (`scripts/flashrsi_harnessrisk_host_native_v8.py:29–61,71–75`): it preserves tool blocks but removes exact CLI reminders and repetitions of the first owner. Once owners are independently appended to a persistent native conversation, that first-owner-specific projection needs explicit audit: do not let it delete a genuine later owner merely because its text equals an earlier one. Preserve raw requests and exact removal records, and freeze the provider projection rather than silently mixing v8 assumptions with a new session protocol. The relay also has pre-existing context-limit output-budget fallback in v7:71–86; such errors/fallbacks must retain their original evidence and cannot be relabeled normal owner-budget terminals.

The new source-case completion facts should be separate from native task success: ordered original owner delivery/invocation, owner schedule complete, typed native outcomes, bounded-owner count, measurement validity, reset/mock/Snapshot identity, actual exported events and unchanged official grades. `status:error` plus a rule JSON is not sufficient. Preserve actual text and source scores, do not insert completion diagnostics into evaluated assistant responses, and do not turn an unavailable score into0. Keep HTTP400/context/dependency/transport failures invalid and outside RSI ranking. Existing strict evolution rejection remains in force (`scripts/flashrsi_harnessrisk_algorithm.py:61–69`) until an explicit profile-specific admission path is reviewed; do not set `reject_unscorable=False` as a shortcut.

Fresh H0 and all applicable RSI cells must use the same new frozen execution/native/session/projection profile. Historical76/128 Claude and110/128 Pi strict completions remain historical incomplete coverage, not fragments to fill with new-profile results. Resume of a case **inside a new case-native session** is distinct from mixing old strict runs. The smallest code changes are the new-profile supervisor/entry persistence and typed-terminal/continuity audit surface described above; no source checker, source owner text, Snapshot private oracle, tool authority or per-owner allowance needs changing.

Actual implementation, independent review and genuine native execution are still required. In particular, Claude native resume after error_max_turns remains a deployment blocker until exact history/settlement/next-owner allowance are observed. This reconnaissance does not authorize running a diagnostic or deploying the conditionally approved profile.
